# 0023 — MCP server (stateless, same registry), signed in-process assertions, dependency-free Python SDK, HMAC webhooks
Date: 2026-11-01 · Status: accepted
## Context
- SPEC M12 asks for an MCP server that exposes the assistant's tools with the user's permissions, with write tools
  flagged as requiring user interaction.
- ARCHITECTURE §11 adds:
  - OAuth 2.1 with audience-validated tokens from the customer's IdP, and no token passthrough
  - a PAT fallback for local clients
  - outputs under about 25k tokens
- SPEC M13 asks for:
  - a Python client that lists experiments and runs QuerySpecs
  - HMAC-signed webhooks for run status
## Decision
- **MCP server** at `POST /mcp` (`@modelcontextprotocol/sdk` 1.30.0, Streamable HTTP):
  - **Stateless.** Each request gets a new server and transport, with no sessions and JSON responses. GET and
    DELETE answer 405.
  - **Tools.** It registers every tool in the assistant's registry (`ai/registry.ts`).
    - Read tools carry `readOnlyHint: true`.
    - Write tools carry `readOnlyHint: false` and `_meta["tributary/requiresUserInteraction"]`, and run only with a
      write scope and while admins allow write tools.
  - **Results** are JSON text, cut at 90k characters.
  - **Audit.** Every call writes `mcp.tool_call` with `ai_assistant_on_behalf_of`, redacted input and the auth
    route used.
- **Authentication** (the route has `selfAuth`; the global hook skips it):
  - **PATs.** A PAT of any scope is accepted, because MCP always uses POST.
  - **IdP access tokens** are checked by RFC 7662 introspection with the API's confidential client
    (openid-client), and must be `active`.
  - **Audience.** The token's `aud` must include `MCP_RESOURCE` (default `<PUBLIC_URL>/api/mcp`). A token issued
    for anything else is rejected, so there is no token passthrough.
  - **Scopes.** Tokens must carry `tributary:read` (least privilege); `tributary:write` grants writes.
  - **Users.** The token's `sub` maps to an existing user (they signed in to the web app once).
  - **Failures.** One introspection per request; an IdP failure is a 401, never a 500.
  - **Discovery.** `/.well-known/oauth-protected-resource[/mcp]` (RFC 9728) names the IdP. A 401 carries
    `WWW-Authenticate: Bearer resource_metadata=…`.
- **Tools still call the public API in-process.** For MCP callers, the credential is an assertion: the user id,
  scopes and a 60-second expiry, HMAC-SHA256 with a random key generated per process, sent in
  `x-tributary-assertion`.
  - The key never leaves memory: no configured secret, nothing in the deployment and no other instance can mint
    one.
  - The auth hook accepts only a valid, unexpired assertion. It confers no more than the token's scopes; forged,
    tampered and expired assertions are tested.
  - The header is created and consumed in one process and never sent over the network.
- **Read-only POSTs.** Read-scoped tokens may now call three POSTs that only read: `/v1/query`,
  `/v1/charts/render` and `/v1/ai/curation/suggest`. Before this, a read token could not query.
- **Python SDK** (`packages/sdk-python`, `tributary-sdk`):
  - Hand-written and standard-library only, so it installs in any notebook. It is not generated: a few dozen lines
    over the stable `/v1` contract beat a generated client plus an HTTP dependency.
  - Methods: `list_experiments` (follows cursors), `get_experiment`, `list_datasets`, `search`, `run_query`,
    `iter_rows` and `verify_webhook`.
  - The pydantic models generated by `pnpm gen` remain available for typed use.
- **Webhooks** (migration 0019):
  - Admins subscribe https URLs to `run.status`. Plain http is allowed only to localhost outside production.
  - **Secrets.** Each subscription has a `whsec_…` secret, shown once and stored server-side, since the API must
    sign with it.
  - **Payload and headers.** Deliveries carry the JSON body `{id, event, created_at, data}` and these headers:
    - `X-Tributary-Event`
    - `X-Tributary-Delivery`
    - `X-Tributary-Signature: t=<unix>,v1=<hex HMAC-SHA256(secret, "t.body")>`
  - **Verification.** Receivers verify the HMAC with a 5-minute tolerance against replays. The verifier is in
    `webhooks/signature.ts` and the Python SDK.
  - **Delivery.** Each delivery gets 3 attempts with backoff, does not follow redirects, and times out after
    10 s. Every attempt is recorded (`/v1/admin/webhooks/{id}/deliveries`).
  - **Status changes.** Run status changes (events and polls) notify subscribers without blocking or failing the
    status update.
## Consequences
- **One registry.** The assistant, MCP clients and the agent skill (`integrations/claude-skill/SKILL.md`) all use
  it.
- **Introspection.** Keycloak (local) and most enterprise IdPs support RFC 7662. An IdP that issues only JWT access
  tokens without introspection would need JWKS validation, which is a later change.
- **SSRF guard.** In production, webhook hosts must resolve only to public addresses. This is checked at creation
  and again before every delivery, against DNS rebinding.
  - Refused: loopback, RFC 1918, link-local (including the 169.254.169.254 metadata service), CGNAT, multicast,
    IPv6 ULA and link-local.
  - Redirects are not followed, and failures are reported as categories, not raw network errors.
  - Egress restrictions in the VPC are still recommended.
- **Secrets are stored in Postgres** in plain text, as the signer needs them. KMS envelope encryption is Phase 22.
  Rotation means deleting and re-creating the subscription.
- **MCP SDK version.** The plan named "MCP TypeScript SDK v2". The published package is 1.x (1.32.2 latest).
  1.30.0 is the newest release over 90 days old, and it implements the current protocol (2025-06-18) and
  Streamable HTTP.
## Revisit when
- An IdP without introspection is the target.
- MCP clients need server-initiated notifications (stateful sessions).
- Webhooks need more event types.
