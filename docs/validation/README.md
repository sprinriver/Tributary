# Validation pack

Tributary is **not a validated system**. It provides the controls that regulated work needs, and this pack helps
a customer validate their own installation for their intended use. Examples of such work are data feeding GLP
studies or regulatory submissions.

Validation stays the customer's process and responsibility. Typically their QA owns it, under their computerised
system validation (CSV/CSA) procedure.

## What is in the pack

| File | What it is |
|---|---|
| `TRACEABILITY.md` / `.csv` | Every requirement (feature ID), how it is verified (automated tests or a command/document check), the evidence (test files and titles) and its status. It is generated by `pnpm run validation:pack`, and `pnpm check` fails if it is stale or a requirement marked passing has no evidence. |
| `IQ_TEMPLATE.md` | Installation qualification: checks that the installation matches the release and its configuration. |
| `OQ_TEMPLATE.md` | Operational qualification: checks that the functions you rely on work as specified, in your installation. |
| `PART11_CONTROLS.md` | How Tributary's controls map to 21 CFR Part 11 §11.10 and Subpart C. It also says which items are procedural (the customer's), and where the product only partly covers a clause. |

## How a customer uses it

1. **Plan:**
   - write a validation plan;
   - define the intended use and the GxP-relevant functions;
   - assess risk, scaling testing to risk as CSA encourages.
2. **IQ:** run `IQ_TEMPLATE.md` against the installed release. The support bundle (Admin → Health → Download
   support bundle) records versions, migrations and health in one file to attach as evidence.
3. **OQ:**
   - attach the CI run for the release commit (all automated tests, linked to requirements in
     `TRACEABILITY.md`);
   - run the manual checks in `OQ_TEMPLATE.md` for the functions in scope, in your installation.
4. **PQ:** test your own workflows with your own data and SOPs. This is customer-specific.
5. **Report and release:** summarise, record deviations, and approve for use.
6. **Change control:** with each new release, repeat IQ and the OQ items for what changed (see `CHANGELOG.md`) and
   re-run the risk assessment.

## What the vendor provides with each release

- The CHANGELOG.
- The traceability matrix.
- The CI results (`check`, `e2e`) for the release commit.
- The SBOM.
- The licence scan.
